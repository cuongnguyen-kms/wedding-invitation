# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev              # Start dev server
npm run build             # Next.js production build (server-rendered, not static export)
npm run start             # Serve the production build
npm run lint               # ESLint
npm run test               # vitest run (all tests)
npx vitest run lib/invitation-experience.test.ts   # single test file
npx vitest run -t "test name"                      # single test by name
npm run db:seed            # Seed the local SQLite database (also runs via `npx prisma db seed`)
npx prisma studio           # Browse/edit the local database in a GUI
npx prisma migrate dev --name <name>   # Create + apply a new migration after editing prisma/schema.prisma
npm run db:generate:postgres   # Generate the Postgres-flavored client (see docs/deployment-postgres.md)
npm run db:migrate:postgres    # Migrate a Postgres database using prisma/schema.postgres.prisma
```

## Architecture

**Current state vs. planned docs:** `AGENTS.md`, `docs/implementation-plan.md`, and `docs/superpowers/specs/2026-05-15-wedding-invitation-design.md` describe the full planned system (Prisma + SQLite guest database, `/invite/[slug]` personalized URLs, admin CRUD, RSVP API) but predate most of the Optional Enhancements — treat `TASKS.md` as the authoritative current checklist, not those docs. As of the Optional Enhancements pass: the data layer, public personalized-invitation routes, RSVP submission, full admin guest CRUD, HTTP Basic Auth on all admin/guest-management routes, CSV guest import/export, per-guest QR codes, a DB-backed wedding settings editor, and a DB-backed managed photo gallery are all built. Only two Optional Enhancements remain undone: session-based admin login (Basic Auth is the intentional lighter-weight stand-in) and Playwright end-to-end tests.

**Admin routes are gated by `proxy.ts` (HTTP Basic Auth), not by the auth on Optional Enhancements' roadmap.** `proxy.ts` (Next.js 16 renamed the `middleware.ts` file convention to `proxy.ts` — same API, exported function is now named `proxy` not `middleware`) matches `/admin/:path*`, `/api/guests/:path*`, `/api/settings/:path*`, and `/api/photos/:path*`, and checks credentials against `ADMIN_USERNAME`/`ADMIN_PASSWORD` env vars, returning 503 if they're unset and 401 with a `WWW-Authenticate` challenge on bad/missing credentials. Two route families are deliberately **not** gated: `/api/invitations/[slug]/rsvp` (guests submit RSVPs without logging in) and `/api/photos/[id]/(thumb|full)` (the public invitation pages render these `<img>` sources for anonymous guests) — the latter is carved out of the matcher's blanket `/api/photos/:path*` coverage by an explicit regex check at the top of `proxy()`, since Next's matcher syntax can't itself express "this prefix except this suffix" cleanly. Local dev credentials live in the gitignored `.env` (`admin` / `changeme`); `.env.example` documents the var names with empty placeholders. Change the real credentials before deploying anywhere reachable by the public.

**Deployed as a server app, not a static export.** This was originally a GitHub Pages static export (`output: "export"`), but that was dropped once Prisma/DB-backed routes were needed — GitHub Pages can't run a database or server-rendered dynamic routes. `next.config.ts` now has no `output: "export"`, no `basePath`/`trailingSlash`/`assetPrefix` GitHub Pages logic, and there's no GitHub Actions deploy workflow; deploy this to a platform that runs a real Next.js server (e.g. Vercel). `publicPath()` in [lib/public-path.ts](lib/public-path.ts) still exists from the GitHub Pages era and is safe to leave in place (it no-ops when `NEXT_PUBLIC_BASE_PATH` is unset), but there's no need to reach for it in new code.

**Prisma uses driver adapters (Prisma 7), not the old implicit env-URL connection.** `lib/db.ts` constructs `PrismaClient` with an explicit `@prisma/adapter-better-sqlite3` adapter reading `DATABASE_URL` — this is required in Prisma 7 and differs from most Prisma tutorials/docs online. The generated client lives at `lib/generated/prisma/` (gitignored — the whole `lib/generated/` tree is, including the Postgres variant below — regenerated via `npx prisma generate`, which also runs automatically on `npm install`/`prisma migrate`). `prisma.config.ts` (not just `.env`) is what the Prisma CLI reads for the datasource URL. Three models: `Guest`, `WeddingSettings` (singleton, id always `"singleton"`), `Photo`.

**Deploying with Postgres instead of SQLite is a deliberate manual swap, not an env toggle — see `docs/deployment-postgres.md`.** Prisma 7's driver-adapter model bakes dialect-specific query generation into the client at `prisma generate` time, so a client generated from the SQLite schema can't just have its adapter swapped to run against Postgres. `prisma/schema.postgres.prisma` + `prisma.postgres.config.ts` are a parallel, hand-kept-in-sync schema/config pair (`npm run db:generate:postgres`, `npm run db:migrate:postgres`) that generate a separate client at `lib/generated/prisma-postgres/`; switching means replacing `lib/db.ts`'s contents per the doc, not flipping a `DATABASE_PROVIDER` var. `@prisma/adapter-pg`/`pg`/`@types/pg` are currently `devDependencies` (needed locally to generate/migrate) — move `@prisma/adapter-pg` and `pg` to `dependencies` when actually deploying against Postgres.

**Guest data layer.** [lib/guests.ts](lib/guests.ts) has the CRUD + RSVP helpers (`listGuests`, `getGuestById`, `getGuestBySlug`, `createGuest`, `updateGuest`, `deleteGuest`, `updateRsvpBySlug`), all validated through the Zod schemas in `schemas/guest.ts` (admin create/update — `updateGuestSchema` is `createGuestSchema`'s fields made `.partial()` *without* carrying over the `guestCount` default, so a partial update never silently resets it) and `schemas/rsvp.ts` (`rsvpSubmissionSchema` is `.strict()` so a public RSVP payload can never smuggle in private fields like `phone`/`email`/`slug`). Slug generation lives in [lib/slug.ts](lib/slug.ts): `slugify()` is a pure, Vietnamese-diacritic-aware function; `generateUniqueSlug()` takes an injectable `isSlugTaken` check so it's unit-testable without touching the real database.

**Personalized invitation routes.** `app/invite/[slug]/page.tsx` loads the guest via `getGuestBySlug`, calls `notFound()` (rendering `app/invite/[slug]/not-found.tsx`) if missing, and only ever passes `name`/`invitationTitle` into the `weddingConfig.guest` shape passed to `InvitationPage` — never phone/email/group/message, to keep the public route from leaking private guest fields. `app/i/[slug]/route.ts` is a short-link redirect to `/invite/[slug]`; it uses `NextResponse.redirect()` rather than `redirect()` from `next/navigation` (the latter hung indefinitely when used inside a Route Handler during testing — stick to `NextResponse.redirect()` for Route Handlers).

**The root `/` route is intentionally non-personalized and does not simulate a guest.** `app/page.tsx` never passes an `rsvp` prop to `InvitationPage`, and `InvitationPage` uses `rsvp`'s presence/absence as the single signal for "is this a real personalized visit": when `rsvp` is undefined it passes `guest={undefined}` to `InvitationCover` (which skips rendering `GuestGreeting` entirely rather than showing a placeholder name) and skips rendering the RSVP/guestbook `Section` altogether. `/invite/[slug]` always supplies `rsvp`, so both show up there. Don't reintroduce a `guestSlug`-optional "demo mode" in `RsvpForm` — its prop is deliberately required now, since the component is never rendered without a real guest.

**Content is DB-backed with `weddingConfig` as the fallback/default, not the single source of truth anymore.** [lib/wedding-config.ts](lib/wedding-config.ts)'s typed `weddingConfig` object is still where the *shape* of wedding content is defined and still what `prisma/seed.ts` seeds the DB from, but `app/page.tsx` and `app/invite/[slug]/page.tsx` now call `getWeddingContent()` from [lib/settings.ts](lib/settings.ts) (couple/date/events/schedule/story/families/location — editable at `/admin/settings`) and `listGalleryPhotos()` from [lib/photos.ts](lib/photos.ts) (gallery — editable at `/admin/photos`), spreading them over `weddingConfig` (`{ ...weddingConfig, ...content, gallery }`). `getWeddingContent()` falls back to `weddingConfig`'s static values if the `WeddingSettings` singleton row hasn't been seeded; the gallery falls back to `weddingConfig.gallery` only when zero photos have been uploaded (an uploaded gallery of any size fully replaces the static one, it doesn't merge). Music and the guest-specific greeting/name are **not** DB-backed and still come straight from `weddingConfig`/the `Guest` row — don't assume every field on the merged config is admin-editable.

**Wedding settings editor** (`/admin/settings`, `GET`/`PATCH /api/settings`) covers text/date content only, by design (photos are a separate feature, music is not editable at all). [schemas/settings.ts](schemas/settings.ts) validates the input shape; [lib/settings.ts](lib/settings.ts) serializes the array/object fields (`events`, `schedule`, `story`, `families`) to JSON text columns on `WeddingSettings` rather than using Prisma's `Json` type, to sidestep any SQLite/Postgres `Json`-handling differences — deserialize on every read. `SettingsForm` (components/admin/SettingsForm.tsx) is a single large client component with per-section array state (add/remove rows for events/schedule/story, comma-separated text for family parent names); it edits a `datetime-local` input in the browser's local timezone with no explicit offset handling, which is an accepted simplification for a single-family app, not an oversight.

**Managed photo gallery** (`/admin/photos`, `POST /api/photos`, `PATCH`/`DELETE /api/photos/[id]`) stores photos as raw bytes in SQLite (`Photo.thumbData`/`fullData`, both `Bytes`) rather than external object storage, so it works unmodified on Vercel's ephemeral filesystem. [lib/photos.ts](lib/photos.ts)'s `createPhoto()` uses `sharp` (moved from `devDependencies` to `dependencies` since it now runs at request time, not just in `scripts/optimize-images.mjs`) to generate both a thumb (700px) and full (1920px) JPEG variant at upload time — always re-encoded to JPEG regardless of input format. `GET /api/photos/[id]/thumb` and `.../full` serve the raw bytes and are the two routes carved out of Basic Auth (see above); everything else under `/api/photos` is admin-only. Reordering (`PATCH` with `{ move: "up" | "down" }`) swaps the `order` field with the adjacent photo in a transaction rather than renumbering the whole list.

**CSV guest import/export** (`/admin/guests/import`, `GET /api/guests/export`, `POST /api/guests/import`) uses a small hand-rolled RFC4180-ish parser/writer in [lib/csv.ts](lib/csv.ts) (`parseCsv`/`toCsv`, unit-tested in `lib/csv.test.ts`) rather than a dependency — the guest data model is simple enough not to need one. Export respects the current `/admin/guests` filters (`q`/`group`/`rsvpStatus`) via query params and includes a computed `invitationUrl` column. Import processes rows independently: a bad row (validation failure, duplicate slug) is collected into a per-row `errors` array and skipped, it does not abort the batch — this matters for re-importing a previously-exported CSV, which will report every row as a slug conflict rather than failing outright.

**Per-guest QR codes** (`GET /api/guests/[id]/qrcode`, linked from `AdminGuestTable` and the guest edit page) are generated on-demand via the `qrcode` package (`QRCode.toBuffer`), encoding `${origin}/invite/${guest.slug}` as a 480×480 PNG. Not cached beyond `Cache-Control: private, max-age=3600` — regenerated per request rather than stored, since generation is cheap and this keeps it correct if a guest's slug ever changes.

**Composition root:** [components/invitation/InvitationPage.tsx](components/invitation/InvitationPage.tsx) owns the single `isOpened` boolean and composes the whole page: `InvitationCover` → `MusicPlayer` / `AutoScrollController` (both react to `isOpened`) → a sequence of `Section`-wrapped content components (`CoupleHero`, `EventDetails`, `CountdownTimer`, `LoveStoryTimeline`, `MapSection`, `PhotoGallery`, `RsvpForm`) → `ClosingMessage`.

**Opening interaction:** tapping the cover's open button in `InvitationCover` calls `dispatchInvitationOpenEvent()` (a custom `window` event defined in `MusicPlayer.tsx`), which `MusicPlayer` listens for to start audio playback. This indirection exists because mobile browsers only allow audio to start from a real user gesture — don't try to autoplay music from a `useEffect` on `isOpened` instead.

**Auto-scroll math is extracted and tested.** The scroll/easing logic that drives `AutoScrollController` (when to start, computing the next section index, cubic easing, continuous scroll position, and detecting a user-interaction click that should cancel auto-scroll) lives as pure functions in [lib/invitation-experience.ts](lib/invitation-experience.ts), covered by `lib/invitation-experience.test.ts`. Keep this kind of logic in that file (pure, unit-testable) rather than inlining it into the component.

**Admin dashboard needs `export const dynamic = "force-dynamic"` on plain pages.** `app/admin/page.tsx` queries the DB directly (no `fetch`, no `searchParams`), so Next.js had no signal to render it per-request and silently prerendered it once at build time — the RSVP counts would have frozen at build time in production. `app/admin/guests/page.tsx` doesn't need the export because reading `searchParams` already forces dynamic rendering. If you add another admin/data page that reads Prisma directly without `searchParams`/dynamic APIs, add the same `export const dynamic = "force-dynamic"` or it'll go stale the same way.

**Friendly malformed-JSON errors.** All three write routes (`POST /api/guests`, `PATCH /api/guests/[id]`, `POST /api/invitations/[slug]/rsvp`) use `parseJsonBody()` from [lib/api.ts](lib/api.ts) instead of `request.json().catch(() => null)`. The old pattern fed `null` into `schema.safeParse`, so an unparseable body surfaced as a Zod "expected object, received null" message; `parseJsonBody` distinguishes "body wasn't valid JSON at all" (→ `Request body must be valid JSON`) from "valid JSON but wrong shape" (→ the normal per-field Zod issues). Reuse it for any new write route rather than reintroducing the old `.catch(() => null)` pattern.

**RSVP form always talks to the backend.** `RsvpForm` (components/invitation/RsvpForm.tsx) requires a `guestSlug` prop and POSTs to `app/api/invitations/[slug]/rsvp/route.ts`, which validates with `rsvpSubmissionSchema` and calls `updateRsvpBySlug`. It used to have a `guestSlug`-optional "local-only demo" mode for the un-personalized `/` page; that branch was removed when `/` stopped rendering the guestbook section at all (see above) — there is no longer a code path where this component renders without a real, backend-connected guest.
